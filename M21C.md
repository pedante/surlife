# Surlife M2.1-C — paired real-model-ready prompt evolution

**Opt-in** `surlife --m21c`. This is a new, versioned protocol (`m21c-v1`), separate from the existing, unchanged `--m21` scripted experiment. The default remains 100% offline.

## What changed

- An organism now spends one bounded reflection consultation to propose a general prompt improvement, or none if it has not yet recorded imperfect work. Prompt text is per-agent, versioned and cannot change another organism or the host.
- It compares its parent and candidate on the **same independently generated hidden tasks**: baseline consultation at one tick, candidate consultation at a later tick. There are two distinct matched pairs, with the order and task hashes recorded. All baseline **and** candidate consultations cost virtual energy and count against the host request cap.
- The host only promotes on valid, completed pairs with no invalid attempts or regressions and at least one unit of task-score improvement. A failed or unmetered provider consultation blocks further calls and cannot promote a candidate. This is a **task-score gate**, not yet a proof of net economic improvement.
- Model-dependent results are recorded as a bounded response bank containing typed answers, sanitized failures, usage reports, model identity and hashes of exactly the prompts/messages/task sent. Replay recomputes decisions, prompt hashes, scores, charges and frozen control with **zero** model calls.
- A frozen-versus-frozen control uses the same challenge stream but no LLM calls. Economic advantage must be evaluated after the actual cost of reflection and both arms of evaluation.
- The "weather" in the underlying M0 referee is simply a varying cost regime. There is no soil/harvest simulation, executable model-authored code or world renderer.

## First run — recommended: no API key, zero external calls

```fish
git pull --ff-only
python -m pip install -e '.[test]'
pytest -q tests/test_m21.py tests/test_m21c.py

surlife --m21c --provider fake --seed 17 --ticks 24 \
  --m21-a evolving --m21-b frozen --max-requests 8 \
  --benchmark-out out/m21c-seed17.json

surlife --verify-m21c-file out/m21c-seed17.json
```

The fake provider deliberately associates a particular text hint with a better classic algorithm. **This is not evidence that an LLM discovered the improvement.** GitHub CI runs only this fixture and a mocked OpenRouter transport on Python 3.10/3.13, with no real network.

## Optional real provider pilot — NOT automatically run

**This command contacts an external provider and must be explicitly approved by the operator.** M2.1-C is limited to a *pinned* OpenRouter `:free` model listed in the API catalog with zero input/output token prices and JSON-schema compatibility; actual account charges cannot be guaranteed by price metadata alone. No paid-price models, dynamic `openrouter/free` route, model-generated code execution or silent retries. Total maximum request count is eight, across reflection, baseline, candidate and later work. Model output tokens are limited to 512 each. Unknown usage or provider failure causes a fail-closed stop. See local/provider account policies before enabling.

If you have independently chosen a pinned suitable model and accepted the provider's conditions, both `--m21c-confirm-live` and `SURLIFE_M21C_APPROVE_LIVE=YES` are required; `OPENROUTER_API_KEY` is read from the local environment, never from an organism.

```fish
set -gx SURLIFE_M21C_APPROVE_LIVE YES
# First configure OPENROUTER_API_KEY in your shell; never commit it.
surlife --m21c --provider openrouter --model PINNED_MODEL:free \
  --m21c-confirm-live --max-requests 4 --max-output-tokens 256 \
  --seed 17 --ticks 16 --benchmark-out out/m21c-live-pilot.json

surlife --verify-m21c-file out/m21c-live-pilot.json
```

No live provider pilot has been performed as part of implementing this stage. The real model may never improve; that is a valid result.

## Scientific limitations and safety boundaries

- The organism's consultation scheduling is a trusted, simple metapolicy associated with its state; the LLM **does not yet choose its own arbitrary goals, call timing or tests**. M2.1-C begins using genuine model proposals *when explicitly enabled*, rather than claiming complete autonomous evolution.
- Each candidate's validation covers two matched trials, a conservative plumbing gate but too few to establish out-of-sample generalization. A future preregistered evaluation with multiple seeds and total-training-cost controls is essential.
- The current evaluation holds out trial problems from all live arena tasks, but the model may possess broad domain knowledge. It is not a proof of data contamination immunity.
- Replay independently reconstructs outcomes from **recorded model responses**, not model provider truth. Report hashes detect inconsistent modifications but cannot authenticate a malicious party who can replace both transcript and hash.
- Missing or malformed usage never produces a "zero-cost" success; attempts with unknown usage are reported and block promotion.
- Virtual energy, real request-count and provider-reported tokens are separate. A zero-priced catalog entry is a pricing preflight, **not an actual account-level monetary spending lock**; the operator must independently enforce one.
- Generated Python execution is deferred to M2.2, following adversarial isolation testing.

### Research decision

Run small, varied and preregistered trials, compare the prompt-evolving organism with frozen prompts and strong no-inference/optimal references **after all proposal and evaluation costs**. If no reproducible advantage appears, report it; do not build a more elaborate virtual world.
