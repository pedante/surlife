# Surlife M1.7 — cross-run policy inheritance and held-out promotion

**Opt-in:** `surlife --m17`. M1.7 extends the M1.6 cognition data-state,
without changing the M0-v2 economy or the M1.4 benchmark protocol.

Training uses **1–4 saved, independently verified M1.6-v2 reports**, merges
only incremental `visits`, `trials` and `gain` for each observable context,
and rejects duplicate training puzzles. A training report containing a provider
failure or no successful model decision is rejected; it must be rerun with a
healthy provider. Training is scoped to the exact provider, model, reasoning
level, and output-token budget. Fake-provider history cannot be evaluated with
Gemini or OpenRouter. The baseline is a fresh untrained
adaptive policy; the challenger is the inherited trained state. Both run on
the same deterministic held-out task stream, with identical model choice and
per-arm consultation cap, but **independent provider calls**.

No future task, hidden optimum, generated `trap` label or model internal
thought is an input to the decision policy. Training and holdout are separated
using SHA-256 fingerprints of the public task contents. Evaluation requires
2–4 distinct held-out seeds. A policy snapshot is promoted **only if**:
- inherited final virtual energy never regresses against **either** the fresh
  adaptive control **or** no-inference Greedy on any held-out seed;
- total inherited energy gain is **strictly positive versus both controls**;
- the inherited policy does not increase invalid actions compared with either
  control on any seed; and
- neither evaluated arm experiences a provider failure.

Rejection is an ordinary research result, not a crash. JSON summaries include
`greedy_energy`, `energy_delta_vs_greedy`, `total_energy_gain_vs_greedy`
and explicit `rejection_reasons` for each comparison.

These are deliberately conservative experiment gates, **not statistical proof
of improvement**. With real providers, comparing two independently drawn
responses is not a causal paired-model-output comparison. The maximum
live request authorization is `2 × heldout seeds × max-requests <= 24`;
even fewer may actually be used. No M1.7 run invokes shell actions, tools
or executable model-produced code.

## Simple offline experiment (Fish shell)

First produce training evidence on *different* seeds. Never overwrite an old
report; the CLI rejects an existing destination.

```fish
surlife --m16 --provider fake --a llm --b greedy \
  --seed 17 --max-requests 4 --benchmark-out out/m16-v2-train17.json
surlife --m16 --provider fake --a llm --b greedy \
  --seed 19 --max-requests 4 --benchmark-out out/m16-v2-train19.json

surlife --m17 --provider fake --a llm --b greedy \
  --train-report out/m16-v2-train17.json \
  --train-report out/m16-v2-train19.json \
  --holdout-seeds 101,103 --max-requests 4 \
  --benchmark-out out/m17-v2-holdout.json \
  --promote-policy-out out/m17-v2-promoted-policy.json

surlife --verify-m17-file out/m17-v2-holdout.json
```

**Expected outcome with the fake provider:** the inherited policy may consume
fewer consultations, but its decisions duplicate Greedy, so it cannot beat
no-inference Greedy after cognition fees. M1.7-v2 must report
`accepted: false`, including `no_positive_gain_vs_greedy`, and must
**not** create the promotion file. That is the intended safeguard against the
false positive demonstrated by the old M1.7 gate.

After a **real** promotion with a provider that can improve decisions, inherit
the strategy state in another M1.6 run with the **same provider, model,
reasoning and output-token settings**:

```fish
surlife --m16 --provider google --a llm --b greedy \
  --max-output-tokens 4096 \
  --policy-in out/m17-google-v2-promoted-policy.json \
  --seed 107 --max-requests 4 \
  --benchmark-out out/m16-google-inherited-107.json
```

The snapshot loader accepts **only** the constrained numeric state, bound
provider/model/generation identity and provenance hashes; it does not execute instructions from JSON. Snapshot
hashes are not signatures, and policy provenance is independently verifiable
only with the corresponding complete M1.7 report.

The policy file is created **only if** the predefined gate accepts the
candidate. The trained state is deliberately never merged with the held-out
outcomes; repeated tuning against those held-out seeds would invalidate the
evaluation. Snapshots are data-only provenance records, not automatically
loaded executable behavior.

Live Gemini training and evaluation must **both** use `--provider google`,
the same reviewed model and generation settings, and a privately supplied
`GOOGLE_API_KEY`. Begin with small `--max-requests 1` or `2`; each
held-out arm makes independent billable requests. A 503/429 causes a rejection
without implying the policy is inferior. For reliable analysis use multiple
independent training/validation splits, cold starts, matching real inference
costs and stronger task families.

## Evidence and limitations

The M1.7 JSON bundle embeds the training M1.6 reports and both complete
held-out arm reports. The offline verifier replays all referee transitions,
adaptive-policy updates, lineage arithmetic, task independence, cohort
comparability, totals, and content hashes. This establishes deterministic
internal consistency, **not cryptographically authenticated provenance**.
Untrusted report content is only parsed as bounded JSON; no report code is
executed. Reports contain no raw provider completions or credentials.

## Protocol migration (v1 → v2)

The original `m16-v1` reports and `m17-v1` evaluation bundles remain
**offline-verifiable** with the same `--verify-adaptive-file` and
`--verify-m17-file` commands. They retain their historical meanings.

M1.7-v2 deliberately **does not accept v1 training files**: M1.6-v1
treated a provider error as negative learning evidence. New M1.6-v2 calls
still pay for attempted consultations, but the policy updates its value
estimates **only after a successful model action**; a rejected or timed-out
provider response is recorded separately and does not teach that reasoning
is useless.

Old `m17-v1` promoted snapshots are no longer loadable by M1.6-v2:
they lack the scoped provider/model/generation identity and were accepted by
a weaker, Greedy-free gate. Regenerate training evidence with new output
filenames. Neither migration nor verification itself incurs provider requests.
