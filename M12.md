# Surlife M1.2 — observable decisions and conservative soul testing

**Opt-in** `--m12` development version. The M0 referee and previous M1/M1.1
commands are unchanged. This stage responds to the real M1.1 pilot on seed 17:
the LLM survived but had one invalid action, 7/12 optimal results versus
Greedy's 11/12; its proposed prompt revision then scored −2 on the four
held-out tasks against 34 for the original soul. The candidate was rejected.

M1.2 is **not** evidence of artificial learning. Its goal is to identify *why*
a model's actions fail, prevent unsound revisions from spreading, and make
provider and virtual-energy expenditure explicit.

## Run (Fish / Arch Linux)

```fish
cd ~/Documents/GitHub/surlife
git fetch origin
git switch --track origin/implementation/m12-robust-selection-20261012
python -m pip install -e '.[test]'
pytest -q
```

Start with an offline M1.2 lifecycle:

```fish
surlife --m12 --seed 17 --ticks 12 --a llm --b greedy --provider fake --cognition selective --max-requests 8
```

Then with a real model, only after checking its free tier is currently listed:

```fish
surlife --check-model
surlife --m12 --seed 17 --ticks 12 --a llm --b greedy --provider openrouter --cognition selective --max-requests 8 --reasoning off
```

Find the resulting `run_id` and inspect the report's `by_action_source` and
`llm_vs_shadow_greedy`. The shadow Greedy policy is scored on each LLM
observation **without changing the model's actual submitted mask, arena
settlement or consultation fee**. It answers whether the LLM achieved a
greater task score than a cheap baseline on those *exact* puzzle instances.
It does NOT measure the long-term counterfactual energy balance or prove
that the LLM caused improvements in survival.

`by_action_source` separates actual LLM action, cheap fallback,
Greedy-during-reflection, and scripted opponent task results. The data-only
ledger remains replayable.

## Evaluate a real pending soul hypothesis

Run evaluation only if the run reports `pending_revisions: 1`:

```fish
surlife --m12 --evaluate-soul out/souls/YOUR_RUN_ID/a.json --provider openrouter --evaluation-seed 3003 --evaluation-tasks 4 --evaluation-cohorts 2 --max-evaluation-requests 16 --eval-min-gain 2
```

This makes at most **16 requests** (4 tasks × 2 cohorts × original and
candidate) and therefore consumes external inference quota. The default
maximum is **24**, enforced before opening a provider request. You may start
with two tasks per cohort (8 requests), but a tiny evaluation is less
informative. A single cohort is not eligible to approve a revision.

The gate accepts a candidate only if:

1. Both prompts were tested on exactly the same new tasks with frozen feedback
   memory, all calls returned usable actions, and task hashes were not present
   in the recorded full lineage (up to 4096 distinct historical tasks).
2. **Each cohort**, independently, gained at least `--eval-min-gain` total
   objective points versus baseline.
3. **No cohort** had more invalid actions than the original soul.
4. There were more paired task wins than losses overall.

Provider failures are logged as a sanitized **aborted** evaluation; the
candidate stays pending and needs a fresh evaluation seed for retry. An
actual candidate regression is logged as **rejected** and the pending
candidate is cleared. Accepted notes alone modify the active prompt.

Important: earlier M1.1 snapshots did not record a full task-hash lineage;
M1.2 does **not** pretend the last eight memory entries represent all prior
tasks. To use the new contamination-aware evaluation, create a **fresh M1.2
organism** (or inherit from a verified full-history M1.2 snapshot). Old
snapshots can still be read, but evaluation with incomplete history fails
closed.

## Interpretation and limits

- This is a conservative heuristic acceptance gate with two or more
  deterministic sets of objective puzzles, **not** a statistical guarantee
  of generalization. Repeated runs and independent confirmation sets remain
  essential, and underlying free-model versions/infrastructure may change.
- The current task is still a five-item subset-selection problem often
  solved well by cheap Greedy. True gains might require new arena task families
  of different complexity; M1.2 intentionally does not change the referee
  to maintain comparability with previous experiments.
- The `--cognition selective` heuristic is host-owned and follows M1.1's
  bounded schedule. The agent has no authority over the provider key, hidden
  referee state, system calls or filesystem.
- The model can still submit an illegal action. It is scored as illegal and
  **not silently corrected**. The legality and shadow baseline diagnostics
  make such failures measurable.
- Snapshots persist outcome and task fingerprints, bounded to 4096 distinct
  hashes, and fail closed if truncated. Snapshots are data-only and hashed
  against accidental changes, not a malicious-host trust boundary.
- The provider quota and the organism's virtual energy are **separate**;
  held-out evaluations consume provider calls but never debit the arena
  ledger. Do not place real secrets in prompts, soul text or logs.
