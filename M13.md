# Surlife M1.3 — admissible action menus (opt-in)

M1.3 tests whether a constrained, trusted **action interface** lets a small free
LLM make useful resource-allocation decisions. It is NOT prompt evolution
or proof of increasing intelligence.

## Evidence behind this experiment

On the first real M1.2 run (seed 17, 12 ticks) all **four** LLM actions were
invalid. The shadow Greedy model solved all four corresponding puzzles legally
and beat those LLM decisions by 118 total objective points. The two-cohort
soul-revision evaluation also rejected the candidate: two cohorts had gains
−2 and 0, with no paired wins. The LLM produced syntactically valid JSON,
but failed to respect the *capacity* constraints.

M1.3 changes the **information/interface**, not the referee's underlying
puzzle, scoring, costs or payout rules. It deliberately removes the need for
the LLM to enumerate feasible subsets, but it still must choose among them
based on each item’s value. No optimal score, top-ranked mask or total reward
per mask is revealed.

## What changes in the menu

For each task the trusted host enumerates *all* subsets with total cost no
higher than `capacity`. The organism sees records containing just a mask ID and
its selected item cost. It still receives original items (cost, reward) and
capacity, and has to compare their potential reward itself. A per-task
strict JSON schema constrains `mask` to those feasible IDs and forces
`soul_update=""` in action calls; reflection is on a later charged tick as in
M1.1.

**No silent correction**: if a provider ignores the schema and chooses an
unlisted mask, the model's actual action is submitted to the referee and
scored as invalid, while the request still costs virtual energy.
The violation is recorded, distinct from a parsing/transport failure.
A model that wants to wait must use the `raw` contract in this experiment.

The protocol is stored on each organism's soul snapshot and run manifest.
M1.3 rejects inheritance/evaluation under a different contract; a raw-mask
soulline cannot be compared as if it had always seen legal menus.

## Evaluate a staged revision under the SAME action contract

```fish
surlife --m13 --evaluate-soul out/souls/YOUR_RUN_ID/a.json --provider openrouter --action-contract menu --evaluation-seed 4009 --evaluation-tasks 2 --evaluation-cohorts 2 --max-evaluation-requests 8
```

The evaluation runs a matched legal-menu for baseline and candidate souls
on each held-out puzzle, using up to eight real OpenRouter requests. It
records contract violations and requires non-regression across all cohorts.
A saved raw-contract soul must instead be evaluated with
`--action-contract raw`. These operations never debit the arena's virtual
energy, but count against external OpenRouter quotas.

## Scientific limitations

- Giving legal choices is **environment-provided feasibility computation**.
  Better outcomes are evidence of a more usable agent interface, not acquired
  arithmetic skill or automatic learning.
- Even a menu-backed LLM can choose low-value legal options. It is still
  competing against a strong nearly-optimal Greedy baseline, and each model
  call costs survival energy. To be viable, extra cognition must buy extra
  utility or run only when needed.
- Provider-side JSON-schema constraints can be unsupported or ignored.
  The trusted referee independently evaluates all actions; CI has no live
  provider calls. Never execute model-generated code or grant a model
  secret/host access.
- M1.3 leaves the M0 game, M1 integration and M1.1/M1.2 modes unchanged.
  Inference tokens/provider quotas and simulation energy are separate budgets.
